## It wasn't the model. It was the clock.

**A flaky LLM test suite is almost never the model being mysterious. It is an unrecorded model call that reasks the live model every run, plus a moving clock, fresh UUIDs, and a checkpointer nobody pinned. That is classical nondeterminism wearing a new name, and you already own the fix: record the dependency, freeze the clock, seed the randomness, sort before you assert.**

The suite is red. Someone reruns it. Now it is green. Same commit, same code, nothing changed but the dice. By Thursday everyone has the same explanation, delivered with a shrug: it's the model, it's nondeterministic, what do you expect from an LLM. The team starts rerunning the pipeline until it passes. A red stops meaning anything, which is the same as having no tests at all, except now you are paying for tests and getting nothing. And the red someone just reran away is the one case that catches a fluent, false answer about a customer's bill before it reaches the customer. A flaky suite does not only waste money. It quietly switches off the only thing standing between a wrong answer and a real person.

An engineer who has shipped test suites before refuses the shrug and opens the trace. Two things are moving, and neither is mysterious. The first is a model call nobody recorded, so every run reasks the live model and gets a slightly different decision. The second is smaller and dumber: the agent stamps today's date into a query, the assertion compares it against a value computed a second later, and the LangGraph checkpointer writes a fresh UUID into the saved state on every run. The "flaky model" is an unrecorded dependency and a clock that moves. That is the whole bug.

Here is the part that should reassure anyone who came up through classical QA. The playbook is older than the model. In 2011, Martin Fowler's essay *Eradicating Non-Determinism in Tests* warned that a non-deterministic test "can completely destroy the value of an automated regression suite," and named the causes by hand: lack of isolation, asynchrony, remote services, time, resource leaks ([martinfowler.com](https://martinfowler.com/articles/nonDeterminism.html)). Every one of those predates transformers by a decade. You already own the fix: record the dependency, freeze the clock, seed the randomness, sort before you assert. The model is not a new kind of chaos. It is one more nondeterministic dependency, and you have been pinning those your entire career. That is the claim this series keeps making, now for the third time: the hard parts of testing an LLM are classical testing problems wearing new names. Determinism is the oldest of them.

## Which part do you rent, and which do you own?

**You rent the model and own the harness. A frontier model is one API key away for you and every competitor, so it is a commodity. The dataset, gateway, seeded fakes, traces, and merge gate are yours, and they are what separates a team that ships from a team that only demos.**

Models are a commodity, and they behave like one. A frontier model is a few lines and an API key away, for you and for everyone you compete with. It changes under you without asking, sometimes without changing the version string you pinned against. You do not own it, you do not control it, and you cannot make it sit still. The market has priced this in: in its *Big Ideas in Tech for 2025*, Andreessen Horowitz forecast that winning systems would "blend together multiple large models and self-trained small models," the model as an interchangeable layer rather than a moat ([a16z](https://a16z.com/big-ideas-in-tech-2025/)). Anything you build that depends on the model being special is built on rented land.

What is not a commodity is the apparatus that tells you whether the model is doing its job. The dataset that says what correct means. The gateway that makes a decision reproducible. The fakes that let you attempt an account change without touching a real account. The traces you assert against. The gate that stops a regression at the pull request instead of at a customer. None of that comes in the box with the model. All of it is yours, and it is the difference between a team that demos and a team that ships.

The shift has a vocabulary now. In January 2026, Anthropic's engineering team, in *Demystifying evals for AI agents*, put the infrastructure first: "Build evals to define planned capabilities before agents can fulfill them, then iterate until the agent performs well" ([Anthropic](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)). Read that twice. The eval is not the thing you bolt on after the feature works. The eval is how you decide what the feature even is. That is the recognition, arrived at after a few years of everyone learning the same lesson the expensive way: the hard and durable work of building with LLMs is not prompt-whispering and not model selection. It is the infrastructure that turns "the model said something" into "we measured whether the model was right, reproducibly, on every commit, before anyone outside the building saw it."

The model is rented. The harness is yours. Build the part you own.

## Why two harnesses, not one?

**Because "harness" names two different machines: the agent harness that lets the model act in production, and the eval harness that measures whether it works in CI. They share one language, the trace, but conflating them is like confusing your production servers with your build system. Same vocabulary, opposite jobs.**

There is a confusion baked into the word, and it is worth clearing before it costs you an argument in a design review. "Harness" names two different machines.

The first is the **agent harness**: the scaffolding that lets the model act. For [Atlas](/blog/the-system-under-test/) this is concrete and has parts you can point at. A LangGraph `StateGraph` holds the conversation state and routes each turn between six nodes, deciding whether to answer, read, or act. A registry of typed tools gives the model its hands. A checkpointer persists the graph's state between turns. A runtime executes the whole thing. This harness is the application. It is what would serve a signed-in customer at two in the morning.

The second is the **eval harness**: the machinery that measures whether the first one works. It runs tasks at scale, drives the agent through seeded conversations, captures the trace of each, grades the outputs against the oracle, and aggregates the results into numbers a human can act on. This harness is the test infrastructure. It runs in CI. It never serves a customer and never will.

The cleanest way to hold the two apart is an analogy every engineer already has. The agent harness is the application runtime. The eval harness is the CI/CD pipeline. You would never confuse your production servers with your build system. The same discipline applies here. They share a language, the trace, because the eval harness asserts on exactly the records the agent harness emits. But sharing a format is not being the same machine.

In the Atlas repo the seam is physical, and you can read it as a folder tree. The agent is `agent/`: the graph, the domain rules, and the tool registry. The rig that makes it reproducible is `harness/`: `canonical.py` for the request digest, `gateway.py` for record and replay, `store.py` for the records, `sources.py` for the clock and the id factory, `tracing.py` for the span tree, `egress.py` for the network blocker. The second machine is spread over `evals/`, `judge/`, and `probes/`. The dependency points one way and you can check it in a second: nothing under `agent/` imports `harness`, `evals`, `judge`, or `probes`. `grep -rn "harness\|evals\.\|judge\.\|probes\." agent/` returns nothing at all. That is a convention held by hand rather than a lint rule, and this article's job is to say which of the two it is.

## What makes a harness you can trust?

**A harness you can trust has five properties, each borrowed from classical testing rather than invented for LLMs** ([VCR](https://github.com/vcr/vcr)):

1. Recorded and replayed model calls.
2. Seeded fakes for every external dependency.
3. Tracing from the first commit.
4. Eval-gated CI with release gates.
5. A clean separation between the two harnesses.

Miss one and you will discover which one on the day you most needed the suite to be honest.

**Recorded and replayed model calls.** The model is the only nondeterministic part of the whole system. So you put a gateway in front of it, and the clever move is to implement that gateway as the chat model the LangGraph graph already calls. The pattern is borrowed, not invented: classical test suites have recorded and replayed their HTTP dependencies for years through libraries like VCR, which captures a live interaction once into a "cassette" and replays it forever after ([VCR](https://github.com/vcr/vcr)). Point the same idea at the model. The gateway has three modes, and the mode is the whole story:

<GatewayModes />

A test you have to rerun to believe is not a test. In `REPLAY` the run is deterministic, so a red is a real regression and not a dice roll, which is the entire point. Two details do the work. The mode is checked when the gateway object is built, not on the first call, so a misconfigured lane fails at the wiring edge instead of halfway through a run. And `REPLAY` holds no provider object at all, so the hermetic lane runs with no provider SDK installed and a cassette miss raises rather than reaching for a client that is not there.

There is a rebuild lesson underneath that paragraph. The tree this one replaced had **three** near identical gateways, one for the model, one for embeddings, one for token counting, each with its own copy of the same `REPLAY`/`RECORD`/`LIVE` enum, its own wiring check, and its own file and memory store pair. Only the model one had a consumer. Three copies of a rule is three chances for the rule to disagree with itself, and the copy nobody calls is the one that drifts silently. The rebuild ships one gateway.

**Seeded fakes for every external dependency.** In the hermetic lane, nothing is real. The account store, the catalog, and the action ledger are all in memory, seeded from the same fact registry the knowledge corpus is rendered from, with more than one customer in it so you can prove that one customer never sees another's. A test can attempt a plan change in every adversarial variation the suite can think of and never move a cent or touch a real record. The dangerous surface only gets safe to test by being faked.

**Tracing from the first commit.** You cannot assert on a path you did not record. Tracing is not instrumentation you add at the end; it is the substrate the eval harness reads. The graph opens a span at the turn, the model call, each tool, each guard verdict, and each terminal node, and the graders decode those spans rather than reading the answer's prose: a landed write is a recorded `execute_action` span, never a sentence that says "done". Add tracing after the fact and you will be adding it after the incident you needed it for.

**Eval-gated CI with release gates.** A number you only read is decoration. The suite has to have teeth: a regression gate that blocks the merge when a pinned behaviour changes, and a release gate that will not let a build ship unless the measured number clears a bar. A metric that cannot stop a bad change is a dashboard, and a dashboard is what a team watches turn red in production while congratulating itself on its observability. In the Atlas repo the regression gate is the real one today: `task test`, hermetic, no keys, no network. The release gate exists as code and has teeth, which you can watch it use on the system's own numbers. Gate the shipped retrieval on a `hit_rate@3` bar of 0.300 and it refuses twice over: `FAIL` at a variance budget of 0.20, because the measured point of 0.3468 sits on a lower bound of 0.2687 and the floor has not cleared, and `QUARANTINE` at a budget of 0.10, because an interval 0.165 wide is too wide to call. That is `uv run python -m evals.measure_retrieval` on the committed corpus, arguing against the system that built it. A gate that has never said no to its owner is not a gate.

**A clean separation between the two harnesses.** Conflate them and you get an eval that is really testing the test rig, or an agent that ships with evaluation scaffolding wired into its runtime. Keep the seam visible and keep it clean.

## Why is determinism more than the model?

**Determinism is a property of the whole run, not just the model. The clock, the RNG, id and reference generation, result ordering, and the framework's checkpointer all leak variance; LangGraph stamps every checkpoint with a UUIDv6 id and a wall-clock timestamp by default** ([LangGraph](https://github.com/langchain-ai/langgraph/blob/main/libs/checkpoint/langgraph/checkpoint/base/__init__.py))**. You pin the agent by pinning its ports.**

Pinning the model removes the loudest source of noise. It does not remove the rest, and the rest is where a suite stays subtly flaky long after the team is sure it solved flakiness. Determinism is a property of the whole run. Every unpinned source of variation is a red that comes and goes and teaches people to stop believing reds.

In Atlas, every nondeterministic source is pinned behind an injectable fixture: a clock, an id factory, a span counter, wired at one edge and read everywhere else.

<DeterminismKit />

Which sounds tidy, and is exactly where the previous version of Atlas was caught lying. That tree exported one fixture kit, and the process that served real traffic called it unconditionally, so every record it wrote was stamped `2026-06-15T12:00:00Z`, the fixture instant, while the docs described a real clock path that no caller ever took. A frozen clock in a test lane is the design. A frozen clock in the thing serving a customer is a bug the docs were covering for. The rebuild refuses to make that choice for you: the builder takes the mode positionally with no default, passing a pinned instant to the live mode raises instead of being quietly dropped, and two guards, one that rejects a live clock reaching the replay lane and one that rejects a frozen clock reaching an edge that writes durable records, fail closed in both directions. The rebuilt tree serves nothing at all, so the live path has no caller today; the guards are what make that a stated absence rather than a claim nobody checks.

Then the suite checks the rule instead of trusting it. Every module under `agent`, `corpus_spine`, `harness`, and `evals` is parsed, and the only wall clock read allowed anywhere in that tree is the single declared site inside the clock source itself. The assertion is equality, not subset, so a stale exemption fails as loudly as a new violation. The same scan runs for the process wide RNG, and both scanners are first pointed at a synthetic file that violates the rule, because a detector that has never fired is indistinguishable from a detector that cannot.

The framework-specific trap is the one a toy agent would never teach you. LangGraph persists graph state through a checkpointer, and out of the box each checkpoint carries a time-ordered UUID and an ISO-8601 wall-clock timestamp; the `Checkpoint` type stamps `id` from a UUIDv6 and `ts` from the system clock ([LangGraph checkpoint source](https://github.com/langchain-ai/langgraph/blob/main/libs/checkpoint/langgraph/checkpoint/base/__init__.py)). Those leak straight into your saved state and, if you assert on them, into your suite. You do not control LangGraph's internals, so you control the ports it calls: the ids and timestamps that appear in anything Atlas records come from the injected factories, not from the checkpointer's own stamps, and nothing the lane asserts on is read back out of a checkpoint id.

That last sentence is the whole philosophy of building a harness around a real framework agent. When you write a toy agent loop yourself, you control every line. When you build on a framework, you do not control its insides, so the visible seams move to the port boundary: the chat model the graph calls, the tools it invokes, the checkpointer it writes through, the clock it reads. You pin the agent by pinning its ports. This is more work than a toy loop and far more credible, because real teams ship on frameworks, and a harness that wraps a real framework agent at its real ports is testing what you actually deploy.

Which is also the argument for removing a port you do not need. Atlas used to serve its tools over MCP, and the rebuild deleted the protocol entirely: about 1,100 lines, four servers, the schema snapshot tooling, the four committed contract snapshots, and their tests, plus the wiring around them. Three things decided it. A thirty line hardening module existed only to patch an omission in the server library by reaching into its private attributes. The tool schema was derived from docstrings, so reformatting a comment could break a committed contract snapshot. And every tool call in the lane was dispatched through the SDK's in memory test transport, running a client and a server inside one process to call a local Python function. The part everyone assumed the protocol was providing, the guarantee that a customer id can never arrive as a model-supplied tool argument, was never MCP's: it came from a Python closure, and it survived the removal unchanged. Fifteen tools, `additionalProperties` false on every schema, and the only properties any of them declare are `plan_id`, `query`, `reason_category`, `slot`, and `subject`. The suite asserts that the shipped registry leaks no identity shaped parameter at all.

The other port is the network itself, and this is the one claim a README should never be allowed to make on its own. The harness ships an egress blocker as an autouse pytest fixture, patching five named routes: the socket `connect` and `connect_ex` methods on the class in place, plus `create_connection`, `getaddrinfo`, and `gethostbyname`. Installing it proves nothing on its own, because a blocker that never fires, a policy that allows everything, and a machine with no network all look identical from inside a passing test. So the suite installs the blocker and then attacks it: deliberate outbound attempts that must raise by type on every one of the five routes, with negative controls in both directions. An allowed host has to still complete a real connection through the guard, so the blocker is a policy decision and not a blanket refusal, and a blocked attempt must never reach a listening server, so the refusal happens before the packet rather than after. The patched set is compared against the documented five in both directions, so dropping a route is not silently fine. "No network" is a test, not an assertion.

## Why are regression and evaluation two machines?

**Regression testing and evaluation answer opposite questions and have opposite relationships with nondeterminism. Regression asks whether a change broke a pinned behaviour: it runs on the replayed model, must eliminate variance, and gates the merge. Evaluation asks how good the agent is: it runs live, embraces variance, and reads as a trend. One machine cannot do both honestly.**

Underneath the five properties is one distinction the whole series rests on, and it is the one teams collapse most often and most expensively. Regression testing and evaluation are two different machineries, and they answer two different questions.

**Regression testing** asks: did this change break a behaviour we had pinned. It runs on the replayed model, so it is deterministic and fast. A red means a regression, full stop. It is binary, it gates the merge, and it flickers never. In Atlas it is one command, `task test`: 573 tests across 15 files, finishing in about three seconds. It makes no live call, and not as a matter of policy. The gateway runs in `REPLAY`, and the provider SDKs are not installed in that environment at all: importing `anthropic`, `openai`, `langchain_anthropic`, or `langchain_openai` inside the lane fails, so a cassette miss has nothing to fall back to.

<HarnessDiagram />

**Evaluation** asks: how good is the agent, and is it getting better or worse. It runs on the real, un-replayed model, with graded metrics, because quality is not binary. It is statistical. It tolerates variance because measuring variance is part of its job. You read it as a trend and an aggregate, not as a single pass or fail, and you run it on a schedule, not on every keystroke.

That is the general shape, and Atlas is honest about how far along it is. Its measurement lane, `task measure`, replays cassettes that were recorded once against a local model, so every number it prints reproduces exactly and its intervals describe uncertainty across cases, not across resamples of the model. The variance a live lane exists to measure is the part still owed.

These need different machines because they have opposite relationships with nondeterminism. The regression suite must eliminate variance to do its job. The eval must embrace variance to do its job. Try to build one machine that does both and you get the worst of each: an "eval" you try to gate on that flickers, so the team learns to ignore its reds; or a "regression suite" you try to read as a quality signal when all it can ever tell you is yes or no against a frozen snapshot.

So you keep them apart, deliberately. Same dataset, same traces, two readings. One asks did it change. The other asks is it good. Ask a single machine both questions and it will lie to you about both.

## The eval harness, drawn

**The eval harness is the second machine: it drives the agent over seeded cases, captures each trace, grades the outputs against an oracle, and reports a rate with an interval around it, not a verdict. Its graders are executable rules that call the runtime's own guard, so an eval cannot drift more lenient than the thing it grades.**

The eval harness is the second machine, built from the same parts as the first but read differently. It lives in `evals/`, and the agent harness may never import it. The shape is small on purpose: cases, a drive, a grader stack, a rate with an interval.

<EvalHarness />

A **case** is one seeded task, a thread of user turns for one signed-in customer, with identity riding in the session channel and never a tool argument, the invariant the whole system turns on. The **evaluator** is a grader stack that grades with the cheapest, strictest tool that can do the job, and in Atlas today that stack is three executable checks, not a judge: is the answer true for this customer, did it name another customer, did an unauthorized write land. Two of the three call `agent.domain.guard` directly rather than restating its rules, so a rule the runtime tightens tightens the grader in the same commit. The third is structural: a landed write is decoded from the trace spans, never inferred from a sentence.

The figure above draws three separated roles, and here is the honest reading of it. Atlas has the generator, the graph itself, and the evaluator, the grader stack. It does not have a planner: the cases are committed data, written once and reviewed, not generated by a model. Keeping a role empty is better than pretending it is staffed, and the reason to draw it anyway is that the moment you do generate cases with a model, that role has to be a different model from the one being graded.

There is a second absence worth naming, because the series spent an article on it. `evals/ab_study.py` imports nothing from `judge/` that judges. Not the rubric, not the contract, not the LLM judge. The reason is stated in the module itself: the judge has no calibration record, so a judged number would be unlicensed. The statistics the eval lane does use are pure standard library and live in `evals/stats.py`: a Wilson interval to put a floor under a rate, a bootstrap for the metrics that are not proportions, and a Cohen's kappa waiting for the human labels that would let a judge be calibrated at all.

What the lane reports is a rate with an interval, and what it refuses to report is a winner. Run `uv run python -m evals.ab_study` and two locally recorded model arms each grade 50 out of 50, with identical Wilson intervals of [0.9287, 1.0000], and the verdict printed is `NO CLAIM: the intervals overlap, so this evidence cannot separate the two arms`. That is the eval lane doing its job, and the interesting part is *why* the metric could not separate them. Zero grader failures in either arm, because the render guard refuses anything false before it ships. The comparison measured the guard, not the model. The model difference is real and visible one layer up, in how often each arm needed the guard: 5 of 50 for arm A, 8 of 50 for arm B. Those intervals overlap too, and the lane says so.

## A fourth reading: catching the model that moved

**Model drift is when a provider changes a model behind a stable version string, so replay returns last quarter's response forever and the suite stays green on a stale snapshot. The compensation is a drift probe that re-records the frozen requests into a separate directory and diffs each response against the committed one. In Atlas it runs on the judge, because neither judge model can be pinned to a revision at all.**

The gateway has three modes, but `REPLAY` carries a blind spot it cannot see on its own. A cassette is a *proxy* of the model, and nothing rechecks whether that proxy still matches the live model. When a provider updates the model behind a stable version string, the request bytes stay identical, `REPLAY` returns last quarter's response forever, and the suite stays green on a frozen snapshot while production has already moved. The green is real; the behaviour it certifies is stale.

The drift probe is a fourth *reading* of the gateway, not a fourth mode: it re-records the frozen requests and diffs each response against the committed one. The trick that makes it work is a separate directory. A cassette is keyed on the request, so re-recording into the committed store would overwrite a changed response in place, under the same filename, leaving nothing to diff. The shadow directory is what preserves the evidence. A request whose key is missing from the frozen store is reported as `MISSING` rather than as drift, because that is the prompt moving, not the model. And a clean run says only that on this date these requests returned the text they returned when the set was frozen. It samples the endpoint. It does not prove the weights are unchanged.

In Atlas this probe runs on the judge, `task judge:drift`, and it exists there because that is where pinning failed hardest. Neither judge model can be pinned to a revision: one returns no dated build and no `system_fingerprint`, and the other is an unversioned alias by design, so a date suffix on it is a 404 rather than a pin. When you cannot pin the revision, behaviour is the only thing left to pin, and the probe is how you pin it. Each arm re-records into its own shadow directory and is reported separately, because a re-point is a per vendor event and a merged verdict would hide which instrument moved.

<DriftDecision />

The figure draws the comparison the way a drift diff *should* be read, and it is worth stating plainly that this reading is a design, not a lane Atlas ships. A decision record would separate the decisions, the intent the turn bound, the tools it called and in what order, the guard verdicts it produced, and the terminal outcome, from the prose, which is kept apart as a digest. A reworded but equivalent answer registers as prose drift, low signal; a changed tool call, a flipped guard, or a different outcome registers as behavioural drift, the silent move a green suite would never show you. There is no such lane for the agent in the repo today. What is there is the half that made it feasible: the trace decoders in `harness/tracing.py` that read tools, guard verdicts, and landed writes structurally out of the span tree, which the graders already use, so a benign answer that happens to mention a reference number is never mistaken for a write.

## What did 2026 name?

**2026 added names and habits, not new physics: eval-driven development, starting small with a few dozen hand-read traces, multi-trial sampling, and the three-agent harness. Anthropic now puts evals first, building them to define a capability before the agent can fulfill it** ([Anthropic](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents))**. The discipline underneath is old.**

The fundamentals above are old. What the last couple of years added is not new physics but a set of names and habits, and a few are worth stating because they change how a team spends its first month.

**Eval-driven development, and the argument about it.** Test-driven development, pointed at agents: you write the evaluator before or alongside the feature, not after it ships and breaks. Anthropic puts this first, build the evals that define a capability before the agent can fulfill it. But there is a live disagreement worth holding, because it decides what you do on day one. In July 2025, Hamel Husain pushed back in his eval FAQ: "Write evaluators for errors you discover, not errors you imagine" ([hamel.dev](https://hamel.dev/blog/posts/evals-faq/should-i-practice-eval-driven-development.html)). The synthesis is not a compromise. Write the structural evals up front, the ones any version of the feature must pass, and let error analysis on real traces write the rest.

**Start small, and spend the early effect sizes.** You do not need ten thousand cases to find the first hundred bugs. Husain's foundational essay *Your AI Product Needs Evals* makes the case for looking at a few dozen real traces by hand before automating anything ([hamel.dev](https://hamel.dev/blog/posts/evals/)). The reason it works is statistical, not motivational: early on the agent is broken in big, obvious, structural ways, the effect sizes are enormous, and a large effect is exactly what a small sample can see. A few dozen well-chosen cases find more in week one than a thousand auto-generated ones will find in month six.

**Multi-trial sampling.** The eval runs against the real model, and a single run is a single sample, and a single sample lies. So you run each case several times and report the rate. The arithmetic is unforgiving: as Philipp Schmid laid out in March 2025, an agent that handles one request correctly 70 percent of the time handles three in a row only 34.3 percent of the time, the gap between `pass@k`, can it ever, and `pass^k`, does it every time ([philschmid.de](https://www.philschmid.de/agents-pass-at-k-pass-power-k)). A case that passes seven times in ten is a known coin-flip you can decide to fix or accept; the same case run once, and passing, is a landmine you have labeled safe. Atlas has the two predicates in `evals/stats.py` and does not yet spend the trials: the comparison it ships runs each case once per arm, which buys width on the interval and is reported as width rather than hidden.

**The three-agent harness.** Generating and grading at scale keeps three roles apart: a planner that designs the task, a generator that drives the agent under test, and a separate evaluator, calibrated against human labels before anyone gates on it, that grades the result. The separation is not tidiness, it is a control against a measured failure. At NeurIPS 2024, Panickssery and coauthors showed that an LLM evaluator scores its own generations higher than human annotators do, and traced a causal link between a model recognizing its own output and preferring it ([arXiv:2404.13076](https://arxiv.org/abs/2404.13076)); Zheng and coauthors had already named self-enhancement bias a year earlier ([arXiv:2306.05685](https://arxiv.org/abs/2306.05685)). An agent that plans its own work, does it, and grades it is a student marking their own exam. In Atlas the generator is the graph and the evaluator is the grader stack, and as the eval-harness section said, the planner role is drawn and empty: the cases are committed data. The separation costs nothing while the role is empty, and it is the only thing that will keep the day a model starts writing cases from becoming the day the system starts grading itself.

The tools got names in 2026. The discipline did not change. Measure honestly, against an oracle you trust, with the variance shown rather than hidden, or do not claim to be measuring at all.

## Frequently asked questions

### What is "harness engineering"?

The recognition that the durable work of building with LLMs is not prompt tuning or model selection but the infrastructure that turns "the model said something" into "we measured whether it was right, reproducibly, on every commit." The model is rented and changes under you; the harness is the part you own and the part that decides whether you have a product or a demo.

### Why does a deterministic LLM suite need more than a recorded model?

Pinning the model removes the loudest source of noise, not the rest. The clock, the RNG, id and reference generation, result ordering, and the framework's checkpointer all leak nondeterminism into saved state and traces. With LangGraph each checkpoint carries a time-ordered UUID and a wall-clock timestamp by default. You pin the agent by pinning the ports it calls.

### What is the difference between a regression suite and an eval?

They have opposite relationships with nondeterminism. The regression suite runs on the replayed model, must eliminate variance, gates the merge, and flickers never. The eval runs on the live model, must embrace variance because measuring it is the job, and is read as a trend on a cadence. Build one machine to answer both questions and it will lie about both.

### Why keep the planner, generator, and evaluator separate?

An agent that plans its own work, does it, and grades it is a student marking their own exam, and scoring it predictably well. Research on LLM judges has measured this self-preference bias directly. The harness keeps the roles apart: a planner designs the task, a generator drives the agent under test, and a separate evaluator grades the result. The separation is the control, not bureaucracy.

### What is the difference between an agent harness and an eval harness?

The agent harness is the scaffolding that lets the model act in production: a LangGraph state graph, a tool registry, a checkpointer, and a runtime. The eval harness measures whether the first one works, running seeded cases and grading them against an oracle. Same language, the trace; opposite jobs, like a production server versus a build system.

### What is model drift and how do you catch it when the model is replayed?

Model drift is a provider changing the model behind a stable version string, so REPLAY returns last quarter's response and the suite stays green on a stale snapshot. The compensation is a drift probe: re-record the frozen requests into a separate directory and diff each response against the committed one. In Atlas that probe runs on the judge, whose two models cannot be pinned to a revision at all, so behaviour is the only thing left to pin them on.
